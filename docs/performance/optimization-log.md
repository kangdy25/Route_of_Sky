# 성능 최적화 작업 로그

모든 개선율은 `(Before - After) / Before × 100`으로 계산합니다. 단계 측정은 방향 확인용 1회 값이며, 최종 판정은 동일 조건 3회 중앙값으로 확정합니다.

## 2026-08-11 · 기준선 측정

- 가설: 최적화 전 상태를 재현 가능하게 기록해야 이후 개선율을 신뢰할 수 있다.
- 변경: 프로덕션 측정 스크립트, Viewer·타일 성능 마크, 측정 프로토콜을 추가했다.
- 원본: `runs/before.json`
- 결과: 배포 산출물 37,522,860 bytes(35.78 MiB), 데스크톱 FCP/LCP 3,528 ms, Viewer 준비 557.7 ms, API 요청 2건·cache hit 0건이었다. 데스크톱 프레임 p95 중앙값은 Rain 849.9 ms, Storm 1,349.9 ms, Snow 1,333.6 ms였다.
- 판단: 최종 측정은 같은 환경·시나리오의 상대 개선율로 평가한다. 헤드리스 Chromium software WebGL의 절대 프레임 시간은 실제 사용자 GPU와 다를 수 있다.
- 롤백 조건: 계측 자체가 앱 동작이나 프로덕션 번들에 런타임 부하를 만들면 해당 observer·mark를 제거한다.

## 2026-08-11 · Weather API 캐시

- 가설: 지역 재방문과 새로고침 때 5분 이내 응답을 재사용하면 외부 요청 수와 데이터 대기 시간을 줄일 수 있다.
- 변경: 좌표별 localStorage 캐시, 강제 갱신, 동일 요청 병합, 이전 요청 취소, 만료 캐시의 네트워크 장애 복구를 추가했다.
- 원본: `runs/api-cache-step.json`
- 결과: 고정 시나리오 네트워크 요청은 2건에서 1건으로 1건·50.0% 감소했고, cache hit는 0건에서 1건으로 증가했다. 캐시 hydration은 데스크톱 0.1 ms, CPU 4배 제한 0.5 ms로 p95 100 ms 목표 안이었다.
- 판단: API 호출 수와 캐시 반영 목표를 통과했다. 최종 3회 측정에서 중앙값을 다시 확정한다.
- 롤백 조건: 좌표가 다른 지역의 데이터가 섞이거나, `force: true`가 캐시를 우회하지 못하거나, 만료 데이터를 정상 네트워크 응답보다 우선하면 캐시 적용을 중단한다.

## 2026-08-11 · 적응형 씬 품질

- 가설: 느린 프레임에서 해상도·날씨 FPS·입자·구름·후처리를 단계적으로 줄이면 저사양 장치의 과부하를 제한할 수 있다.
- 변경: Auto/High/Medium/Low 프로필, 5초 p95 하향·10초 쿨다운·3회 연속 상향 정책, rAF 상태 병합, 변경된 하위 시스템만 갱신, Low 눈 단순화와 객체 재사용을 추가했다.
- 원본: `runs/adaptive-quality-step.json`
- 적용 단계: 20초·1회 측정에서 데스크톱은 High 0.525초 → Medium 5.493초 → Low 15.928초, CPU 4배 제한은 High 1.304초 → Medium 5.988초 → Low 16.980초였다.
- 데스크톱 결과: Rain p95 849.9 → 599.1 ms로 250.8 ms·29.5% 개선, Storm 1,349.9 → 1,083.3 ms로 266.6 ms·19.7% 개선, Snow 1,333.6 → 1,433.3 ms로 99.7 ms·7.5% 회귀했다.
- 저사양 결과: Rain은 1,117.6 → 1,082.9 ms로 34.7 ms·3.1% 개선, Storm은 1,434.0 → 1,433.3 ms로 0.7 ms·0.05% 개선, Snow는 1,533.2 → 1,783.3 ms로 250.1 ms·16.3% 회귀했다.
- 용량 결과: 배포 산출물은 37,522,860 → 37,532,463 bytes로 9,603 bytes·0.026% 증가했다.
- 판단: 단계 전환과 자원 예산 적용은 검증했지만 절대 p95 목표는 미달했고 Snow 1회 값은 회귀했다. 이를 최종 3회 중앙값에서 재검증하며, 번들 증가는 정적 자산 최적화로 상쇄한다.
- 롤백 조건: 최종 3회 중앙값에서도 Snow가 10% 넘게 회귀하고 시각 품질·다른 지표 개선으로 상쇄되지 않거나, 수동 단계가 예고 없이 변경되면 해당 효과 단순화 또는 자동 전환을 롤백한다.

## 2026-08-11 · 정적 자산 최적화

- 가설: 초기 화면에 3,174px PNG 로고를 사용하고 런타임 미사용 GIF를 public에 두는 구조가 배포 크기와 첫 콘텐츠 표시를 지연시킨다.
- 변경: 헤더 로고를 128×128 WebP로 교체하고 고정 크기·비동기 디코딩 힌트를 추가했다. 30초·28초 데모 GIF는 애니메이션 WebP로 변환해 문서 자산으로 분리했다.
- 원본: `runs/static-assets-step.json`
- 로고 결과: 3,872,089 → 5,154 bytes로 3,866,935 bytes·99.87% 감소했다. 크기는 3,174×3,174 → 128×128px이며 50KB 목표를 통과했다.
- 문서 데모 결과: 19,376,792 → 6,673,290 bytes로 12,703,502 bytes·65.56% 감소했다. Demo 1은 30,000ms·299 WebP 프레임, Demo 2는 28,000ms·280 WebP 프레임으로 원래 재생 시간을 유지했다.
- 배포 결과: 직전 단계 37,532,463 → 14,288,823 bytes(13.63 MiB)로 23,243,640 bytes·61.93% 감소했다. 목표 10 MiB보다는 3.63 MiB 커서 미달이다.
- 로드 결과: 1회 단계 측정에서 데스크톱 FCP/LCP는 기준선 3,528 → 1,780 ms로 1,748 ms·49.5% 개선했고, resource transfer는 5,844,142 → 1,980,037 bytes로 3,864,105 bytes·66.1% 감소했다. CPU 4배 제한 FCP/LCP는 3,976 → 2,412 ms로 1,564 ms·39.3% 개선했다. 최종 판정은 3회 중앙값으로 재확정한다.
- 실패 실험: Cesium의 ESM 재빌드는 배포 크기를 14,288,823 → 12,506,663 bytes로 1,782,160 bytes·12.5% 더 줄였지만 앱 JS gzip을 83.59 → 1,183.55KB로 1,099.96KB·1,315.9% 증가시켜 90KB 목표를 위반했다. 초기 다운로드·파싱 비용 회귀가 더 커 채택하지 않았다.
- 판단: 로고, 전송량, FCP/LCP 목표는 단계 측정에서 통과했고 앱 JS/CSS gzip 목표도 유지했다. 남은 12.96MB의 Cesium 런타임 자산을 무리하게 제거하면 지형·텍스처·좌표 변환이 깨질 수 있으므로 배포 10 MiB 목표 미달을 공개하고 CDN·선택 자산 배포를 후속 과제로 둔다.
- 롤백 조건: WebP 미지원 환경이 지원 범위에 포함되면 PNG/JPEG fallback을 제공하거나 지원 범위를 명시적으로 조정한다. 로고·데모의 시각 손상이 확인될 때만 원본에서 더 높은 품질의 WebP로 재인코딩한다. Cesium 자산은 실제 네트워크 요청과 기능 검증 없이 삭제하지 않는다.

## 2026-08-11 · 최종 3회 비교

- 가설: 각 단계의 1회 측정은 변동성이 있으므로 같은 프로토콜의 3회 중앙값으로 전체 효과와 회귀를 다시 판정해야 한다.
- 변경: Before/After 원본에 JS·CSS gzip과 로고 byte를 보강하고, 저사양 지표까지 포함한 비교표·정적 차트·동일 Rain 캡처·사례 연구를 작성했다.
- 원본: `runs/before.json`, `runs/after.json`
- 로드 결과: 데스크톱 FCP/LCP 3,528 → 3,264 ms로 264 ms·7.5% 개선했지만 목표는 미달했다. 저사양 FCP/LCP 3,976 → 3,092 ms로 884 ms·22.2% 개선해 LCP만 통과했다. Viewer 준비는 데스크톱 61.5 ms·11.0%, 저사양 104.6 ms·7.2% 개선해 모두 통과했다.
- 프레임 결과: 데스크톱 Rain 29.4%, Storm 42.0%, Snow 22.5%, 저사양 Rain 25.3%, Storm 24.5%, Snow 20.7% 개선했다. 모든 절대 p95 목표는 미달했다.
- API·전송 결과: API 요청 2 → 1건으로 50.0%, 리소스 전송 5.57 → 2.72 MiB로 51.2% 개선했다. 캐시 hydration은 0.30 ms로 통과했다.
- 빌드 결과: 배포 산출물은 기준선 대비 61.9% 감소했지만 13.63 MiB로 목표 미달이다. 앱 JS gzip은 77.79 → 80.77 KiB로 3.8% 증가, CSS는 14.69 → 14.74 KiB로 0.3% 증가했지만 두 목표 모두 통과했다.
- 판단: 상대 지표는 모두 개선됐고 API·로고·Viewer·저사양 LCP 목표를 달성했다. 미달 항목은 외부 Cesium 런타임과 software WebGL 제약을 명시하고 실제 GPU RUM과 Cesium 초기 long task를 후속 우선순위로 둔다.
- 롤백 조건: After 3회 중앙값보다 후속 릴리스가 10% 넘게 회귀하면 동일 프로토콜을 재실행하고 해당 변경의 기능 단위 커밋을 우선 롤백한다.
