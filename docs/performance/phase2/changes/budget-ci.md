# 정적 성능 예산 CI

## 가설과 Before

Phase 2까지 실제 GPU 측정은 PR 자료로 남겼지만, 번들·배포 산출물·공유 썸네일 크기가 커져도 CI가 이를 차단하지는 못했다. 이 작업은 사용자 체감 시간을 임의로 개선하는 변경이 아니라, 이미 달성한 정적 전송량을 후속 변경에서 되돌리지 않도록 하는 결정적 보호 장치다.

기준선 빌드(캐시 없는 `pnpm run build`)는 app entry JS gzip 86,752 bytes, CSS gzip 14,947 bytes, `dist/` 13,534,839 bytes, `public/thumbnail.jpg` 213,019 bytes였다. 당시 자동 차단은 없었다.

## 변경

- `perf:budget`이 production build의 app entry JS/CSS gzip, 전체 `dist/`, 썸네일 크기를 검사한다.
- `.github/workflows/ci.yml`에서 lint 뒤 build와 예산 검사를 실행한다.
- 실제 GPU 값은 기기·드라이버 변동을 갖기 때문에 CI 실패 조건에 넣지 않고, Phase 2의 3회 원본 측정 JSON으로 검토한다.
- 날씨 E2E는 첫 탐색 전에 테스트 컨텍스트의 이전 선택 지역 캐시만 한 번 비운다. 같은 테스트 안의 새로고침은 `sessionStorage` 표식으로 보존하므로 5분 캐시 시나리오는 그대로 검증한다.

## 고정 예산과 판정

| 항목 | Before | 차단 예산 | After | 절대 차이 | 개선율 | 판정 |
|---|---:|---:|---:|---:|---:|---|
| 앱 entry JS gzip | 86,752 B | 92,160 B (90KiB) | 86,752 B | 0 B | 0.0% | 통과 |
| 앱 entry CSS gzip | 14,947 B | 18,432 B (18KiB) | 14,947 B | 0 B | 0.0% | 통과 |
| 전체 `dist/` | 13,534,839 B | 14,292,091 B (13.63MiB) | 13,534,839 B | 0 B | 0.0% | 통과 |
| 썸네일 | 213,019 B | 256,000 B (250KiB) | 213,019 B | 0 B | 0.0% | 통과 |

Before와 After가 동일한 것은 이 브랜치가 런타임·자산을 변경하지 않았기 때문이다. 개선율은 `(Before - After) / Before × 100`으로 계산했다. 값이 예산을 넘으면 `perf:budget`은 종료 코드 1로 CI를 차단한다.

## 롤백 조건

예산 계산이 app entry가 아닌 임의 청크를 선택하거나, 정상 build에서 거짓 실패를 내면 CI 단계와 스크립트를 되돌리고 측정 방식을 보정한다. 예산 초과는 예산을 올리기보다 변경 원인과 사용자 가치를 PR에서 먼저 검토한다.
